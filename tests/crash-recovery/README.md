# absurd crash-recovery proof

Proves absurd's single most important durability claim:

> **A task survives a real WORKER CRASH and resumes from its last checkpoint
> WITHOUT re-running already-completed steps** (replay from checkpoint /
> exactly-once step execution).

The existing `tests/integration` harness only does a clean, event-driven
suspend/resume. This harness goes further: it kills the worker **mid-task with
`process.exit(1)`** (a real process death, not a graceful shutdown or a thrown
error) and verifies a *fresh* worker process picks the task back up and finishes
it without redoing the work that was already done.

## What it does

1. Spawns a durable task `resilient-job` onto the **`crashtest`** queue through
   the `@keeb/absurd` swamp extension (`maxAttempts=2`).
2. **Worker #1** claims the task, runs the `side-effect` step (which appends one
   unique line to a marker file and is checkpointed), then **crashes via
   `process.exit(1)` while still holding the task's lease** — an authentic crash.
3. **Worker #2** (a separate process) starts. absurd reclaims a crashed task
   only *after* its lease (`claim_expires_at`) expires. We use a **short
   `claimTimeout` of 3s** so the next `claim_task` call sweeps the expired run,
   `fail_run`s it (creating attempt 2), and worker #2 claims attempt 2.
4. On the recovery attempt, `ctx.step("side-effect", ...)` returns its **cached
   checkpoint value without running the body again** (no new marker line), then
   a `finalize` step runs and the task completes.

## The mechanics it relies on

- **Checkpoints survive attempts.** Steps are stored in `absurd.c_<queue>` keyed
  by `(task_id, checkpoint_name)` — *not* by run/attempt — so a completed step is
  replayed on every later attempt of the same task.
- **Claim lease + reclaim.** `claim_task(queue, worker, claim_timeout, qty)` sets
  `claim_expires_at = now + claim_timeout`. A crashed worker leaves its run
  `running` with an expired lease; the next `claim_task` call sweeps expired runs
  (`state='running' AND claim_expires_at <= now`), calls `fail_run` on them
  (which inserts the next attempt when `attempt+1 <= max_attempts`), and then
  claims the fresh attempt.
- **The short-lease knob.** `Absurd.startWorker({ claimTimeout })` (seconds) is
  the exact configuration; `worker.ts` sets `CLAIM_TIMEOUT = 3`.

## Assertions (all must pass)

1. The marker file contains **exactly one line** — the side-effecting step body
   ran once despite the crash + retry (checkpoint was replayed).
2. The task reached **`completed`** (via the swamp `result` method) with the
   expected payload.
3. A retry actually occurred: `attempts >= 2` (and 2 run rows) in
   `absurd.t_crashtest` / `absurd.r_crashtest`.
4. Log evidence of crash-then-resume across **two distinct worker processes**
   (worker #1 logs `CRASH`, worker #2 logs `RESUMED`), and the result payload
   shows the side-effect was done by `w1` while `finalize` was done by `w2`.

## Run it

```bash
tests/crash-recovery/run.sh
```

Requires the deploy Postgres stack running (`postgresql://absurd:absurd@localhost:5432/absurd`)
and the `@keeb/absurd` extension recognized by swamp. The harness creates the
`crashtest` queue if missing, vendors the absurd SDK source, applies the
`pg-shim`, installs its own deps, and prints `PASS`/`FAIL` per assertion plus an
`OVERALL` line. It leaves Postgres running and kills its worker processes on
exit.

## Why a real crash (not a `throw`)

A thrown error would also exercise checkpoint replay at the SDK level, but it is
caught by `executeTask` and turned into an orderly `fail_run` — the worker stays
alive. `process.exit(1)` kills the process with the lease still held, so recovery
genuinely depends on absurd's lease-expiry reclaim path running in a *different*
process. That is true crash recovery, which is what this proves.

## Files

- `worker.ts` — registers `resilient-job`; countable side-effect step + one-shot
  real crash; replays + completes on recovery.
- `run.sh` — full harness: queue setup, SDK vendor, spawn via extension, worker
  lifecycle (crash + restart), status polling, assertions.
- `pg-shim.ts` — ESM/CJS interop shim for `pg` (same as `tests/integration`).
- `absurd-sdk.ts` — vendored absurd TS SDK (regenerated by `run.sh`).
- `package.json` — this subdir's own deps (`pg`), separate from `tests/integration`.
